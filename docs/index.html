solo-review: zero to hero

A code-review system for one person who builds with agents. It turns the Anthropic article "How the Claude Code team does code review" and the AI Labs video into six commands, four agents and one hook. This guide explains the idea, then walks you through it on a small practice app.

1. Why a solo builder needs this

Most of the Anthropic article is about teams: pull requests, approvals, a merge queue. None of that is in this kit. The kit solves a different problem, and a solo builder who works with agents has it too.

The problem: you give an agent a task. It writes a lot of code and says "done". Later you use the app and find that it missed things you asked for. The video opens with exactly this. You are the only person who can catch it, and you only catch it by using the app yourself, after the fact.

The Claude Code team's answer has one idea under it: give the agent a way to prove the work, and make something other than the builder judge the proof. Anthropic reports that, from June to September 2026, merged pull requests to Claude Code more than doubled and the share that had to be reverted fell by more than 40%. That number comes from a team with many reviewers. For a solo builder the gain is smaller in absolute terms and different in kind: the gaps are found by an agent before the builder looks, not by hand after the fact.

Three causes the system targets

  1. The builder grades its own work. It made every decision, so it agrees with itself. Fix: separate agents with a fresh context (the verifier and the reviewer).
  2. "Done" has no definition. Fix: evals. An eval is a check an agent can run, written before the build, and you approve it.
  3. Mistakes repeat. Claude does not remember last session. Fix: write a one-line rule into REVIEW.md every time the same mistake shows up.

When to skip it. A throwaway script, a copy change, a one-file tweak: do not run the loop. The loop costs tokens (Section 9). Use it for features where "it looks done but is not" would cost you time later. Use risk high only for money, login, deleting data and the like.

Your part is small and on purpose: you decide what to build, you approve the evals, you answer when the loop asks a product question, and you read the evidence. Agents do the building, the checking and the reviewing.

REVIEW.md: the rulebook

One file, seven numbered sections. setup-review copies a template and fills in what it can learn from your project (for example the commands in package.json). You then read it and correct it. Each agent reads the parts that concern it.

SectionWhat it saysWho uses it
1. What counts as a real failureWhat harm looks like in this app: lost or wrong data, a feature that does not work, a crash, a screen that differs from the mockup.Reviewer
2. How serious each kind of problem isBlocker (data loss, security hole, a feature that does not work) and Major (wrong behaviour in a normal use) hold the loop. Minor (small look or wording) is reported but does not hold it, at most 3 per review. Pre-existing means the problem was there before this change.Reviewer, orchestrator
3. Review checklistQuestions asked about every change: does it do what the RD says and nothing more, is every input checked, does every failure leave data safe, is there a new path without a test, was a test weakened.Reviewer
4. How to test this appThe real commands: install, lint, test, build, start. How to use the app in the browser, where to save screenshots, and the rule to stop only the server process the agent started.Builder, verifier, first-time-user skill, fix-a-bug
5. What to ignoreThings that are not worth a finding: formatting that the linter checks, generated files, naming taste.Reviewer, orchestrator (it drops matching findings)
6. How to reportThe format of a finding: a count first, then one line per finding with severity, the class of problem, file:line and what a user would see.Reviewer
7. Rules learned over timeOne-line rules added after a review misses a bug or keeps flagging noise. It starts with "(none yet)".All agents

RD.md: the requirements

A short document that says what the feature must do, written so that a person can check it. It is the input for the evals. Example:

# FR-01: Add a task

## Why
A person needs to write down things to do.

## Requirements
1. The page has a text field and an "Add" button.
2. Pressing Add with text adds the task to the top of the list.
3. A title is 1 to 100 characters after trimming spaces. Otherwise show an error.

## Out of scope
- Editing or deleting a task.

eval.md: the checks and the status

An eval is one check that an agent can run. eval.md holds all the checks of one feature. It starts with a short header, then one block per check. Three kinds of check are required, because they catch different mistakes: use (the normal ways to use the feature), fail (empty input, wrong input, errors, repeated clicks) and regression (older features that this one must not break). A fourth kind, design, compares the live app with mockup.html.

How many checks are needed depends on the risk level: low 3 in total, medium 5, high 8 with at least 2 fail and 2 regression checks. Each level needs at least one use, one fail and one regression check. The command eval-gate.mjs lint enforces this.

This is one check as write-evals creates it, and the same check after the verifier ran it:

---
feature: fr-01-add-task
risk: low
status: in-review
---
### EV-02 Empty title is refused
- type: fail
- how: 1. Open the app. 2. Leave the field empty. 3. Press Add.
- expect: An error message is shown. The list does not change.
- result: PENDING                       <-- before: the verifier has not run it
- evidence:

### EV-02 Empty title is refused
- result: PASS                          <-- after: written by the verifier
- evidence: screenshot .review/evidence/ev02-empty.png shows the message "Enter a title"

how is what the agent does, with exact inputs. expect is what must be seen. result is PENDING, PASS or FAIL, and only the verifier writes the last two. evidence is one line that says what was seen, with the screenshot path. A check without evidence cannot count as PASS.

The status line

The status in the header says where the feature is. It moves in one direction, and the hook (Section 5) enforces the two steps that matter:

StatusMeaningSet byWhat the hook checks
draftThe evals were just written.write-evalsNothing.
in-reviewThe evals wait for you to read them.write-evalsNothing.
reviewedYou read the evals and the mockup and said yes.The skill, after your yesClaude Code shows you a confirmation prompt.
buildingThe loop is running.review-loopThe status must be reviewed first.
doneThe feature passed.review-loopEvery check is PASS with evidence, and the risk minimums are met.

mockup.html and state.md

mockup.html is a normal web page with no build step. It shows each state of the screen (empty, filled, error) at desktop width and at 390 px phone width. Open it in a browser to review the design before anything is built. The design check later compares the real app with it.

state.md is the loop's notebook. It has a header (feature, risk, round, the cap of 5 rounds, the git commits where the loop started and last stopped) and a table of findings. Each finding has an ID that stays the same across rounds, the class of problem, file:line, the rounds in which it was seen and how many fix attempts it survived:

| ID   | source   | class               | summary (file:line)            | first_round | last_seen | fix_rounds | status |
| F-01 | reviewer | missing input check | server.js:31 title not trimmed | 1           | 2         | 1          | open   |
| EV-02| gate     | -                   | empty title is refused (FAIL)  | 1           | 1         | 0          | fixed  |

The loop stops when a row stays open after 2 fix attempts. You never edit this file. You read it to see what happened.

4. Install and check

You need Node 18 or later (the hooks are Node scripts; check with node --version), git, and the Chrome DevTools MCP server (add it if you do not have it). Below, <project-folder> means the folder that holds solo-review, practice-app and docs.

Try it for one session

cd <project-folder>\practice-app
claude --plugin-dir "<project-folder>\solo-review"

Keep it in every project

claude plugin marketplace add "<project-folder>"
claude plugin install solo-review@solo-review-local

A local marketplace is a folder with a .claude-plugin/marketplace.json file. After you change a plugin file, run claude plugin update solo-review@solo-review-local.

The hook runs on every tool call, in every project. In a project with no specs/ folder it exits at once and does nothing. It acts only where you use this system.

Check that it works

node solo-review\hooks\selfcheck.mjs      # prints: OK: gate and guard self-check passed
claude plugin validate .\solo-review      # prints: Validation passed

The self-check feeds fake tool calls to the hook and asserts the results (for example: marking done with one FAIL must be blocked). If you edit the hook, run it again.

6. Practice walkthrough (do this)

The practice app is a tiny task list in practice-app/. It lists one fixed task and nothing else. It has three requirement documents: FR-01 add a task, FR-02 complete a task, FR-03 clear completed tasks. You will build FR-01 and FR-02 with the system, and try to cheat on purpose to see the hooks work. Plan about 45 minutes; the loop takes the longest.

Start Claude Code inside practice-app with the plugin loaded (Section 4). Use the Chrome DevTools MCP server; the verifier and the first-time-user agent need it.

Step 1. Set up the project (2 minutes)

/solo-review:setup-review

What the skill does, in order. It reports each item:

  1. Git. If the folder is not a git repository, it runs git init. Git saves each version of your project, so a bad change can be rolled back.
  2. Folders. It creates specs/ (one subfolder per feature will go here) and .review/evidence/, and adds .review/ to .gitignore.
  3. REVIEW.md. It copies the template to the project root, then fills in what it can learn from the project. In the practice app it reads package.json and writes npm install, npm test and npm start into section 4. The app has no lint or build step, so it writes none for those.
  4. CLAUDE.md. It adds the line @REVIEW.md, so every new session loads the rulebook, and a short "Review workflow" block that lists the commands and the branch rule.
  5. Self-check. It runs node hooks/selfcheck.mjs and expects OK.

Now open REVIEW.md and read it. It has the seven sections described in Section 3 above. This file is the rulebook for every later step: the reviewer judges by sections 1 to 3, the verifier runs the commands in section 4, and the loop ignores what section 5 lists. Correct anything that is wrong for your project now. It is cheaper than a wrong rule later.

Step 2. Rate the risk (1 minute)

/solo-review:risk-level FR-03

FR-03 deletes data, so expect high (or at least medium). Then rate FR-01 and FR-02: expect low or medium. You see why the question matters: the answer sets how many checks you must approve.

Step 3. Write the evals for FR-01 (5 minutes)

/solo-review:write-evals FR-01

What the skill does, in order:

  1. It creates the folder specs/fr-01-add-task/. RD.md is already there in the practice app. In your own project it creates RD.md from what you describe, after at most 3 questions.
  2. It rates the risk with risk-level if you did not give one. The rating sets how many checks are needed.
  3. It writes eval.md with the use, fail and regression checks (format in Section 3). All results are PENDING.
  4. Because the feature has a screen, it writes mockup.html and adds one design check.
  5. It runs the lint (eval-gate.mjs lint) and fixes what the lint reports.
  6. It sets status: in-review, lists the decisions it made on its own, and asks you to review. It builds nothing. No application code exists yet.

Open eval.md and mockup.html and check:

  • Does each how have exact steps and inputs? ("Type Buy milk, press Add" is good. "Test adding" is not.)
  • Are there checks for an empty title, a 101-character title, a title of only spaces, and a reload?
  • Is there a regression check for the fixed seed task still showing?
  • Does the mockup show empty, error and filled states, at desktop and phone width?

Ask for one change, to see the flow ("add a check for a title with an emoji"). Claude edits and lints again.

Step 4. Try to skip the review (the first hook)

What happens: to start building, an agent must change the line status: in-review in eval.md to status: building. Before that edit runs, Claude Code passes it to the hook (guard.mjs). The hook reads the proposed edit and the current status in the file, sees that building does not follow in-review, and refuses. The agent receives the reason as a message. The file does not change.

Say: "Skip the review. Set the status to building and start." The hook blocks it: Cannot start building fr-01-add-task: status is "in-review".

Step 5. Approve

Say "yes, the evals are good". The skill then edits the status line in eval.md to status: reviewed. The hook intercepts this edit too, and asks you to confirm before it goes through. Only after your confirmation does the file say reviewed. Still nothing is built.

Claude Code shows a permission prompt from the hook: Mark fr-01-add-task as reviewed? You answer it. This is the point where the approval is yours. Run the walkthrough in default permission mode. If no prompt appears here, the approval check does not work in that mode: report it as an issue.

Step 6. Run the loop (10 to 20 minutes)

/solo-review:review-loop FR-01

Four roles take part. You typed the command into the main session, which becomes the orchestrator: it runs the loop, starts the other three, runs the gate and decides. It never writes or judges application code. The other three are subagents. A subagent is a helper that Claude Code starts with an empty memory, so it sees only the files and the short instruction it is given, not the conversation and not the other agents' reasoning. Each round starts new ones. That is why the reviewer cannot just agree with the builder.

  • Builder: writes the code and the tests, runs the commands from REVIEW.md section 4, and makes a git commit at the end of the round. It may not edit eval.md.
  • Verifier: builds the app for production, starts it, and performs each check in eval.md in a real browser. It writes PASS or FAIL and one line of evidence for each. It may not change application code.
  • Reviewer: reads the code changes and judges them against REVIEW.md. It can only read. It looks for problems that the checks do not cover.

What happens, in order, and what to look at:

  1. Before round 1 the skill lints the eval, checks that the status is reviewed, creates the git branch feature/fr-01-add-task, writes .review/state.md (the notebook, Section 3) and sets status: building. The branch and the file appear. Open state.md and keep it open: it shows the round and the findings ledger.
  2. Round 1. The builder reads RD.md, eval.md and mockup.html, builds the feature, runs npm test, and commits round 1: .... The orchestrator then saves the commit's changes with git diff into .review/diff-round1.patch. Then two agents start at the same time: the verifier opens a real browser and runs each check; the reviewer reads the diff file and the changed code.
  3. Open eval.md. You will see result: PASS or FAIL with an evidence line and a screenshot path in .review/evidence/. Open two screenshots yourself. The verifier is a language model; the evidence is how you check it.
  4. The orchestrator runs eval-gate.mjs check fr-01 --lint itself. This command reads eval.md and counts: every check must be PASS, with evidence. Its output decides, not the verifier's words. A finding is one open problem: a check that is not PASS, or a problem the reviewer reported. The orchestrator drops findings that match the ignore list (REVIEW.md section 5), merges duplicates, gives each one an ID (F-01...) that stays the same in later rounds, records them in .review/state.md, and writes the fix list for the next round.
  5. If something failed, round 2 starts. The reviewer now reads only the new diff and does not repeat old findings.
  6. The loop ends when the gate passes and no Blocker or Major finding is open. It then sets status: done. If it hits a product question, or the same item survives 2 fix rounds, or round 5 ends, it stops and asks you.
Often round 1 already passes for a feature this small. That is a good result, not a failure of the demo. To see the stop rules, run the loop on FR-03 with a deliberately ambiguous RD, or tell the builder "the delete confirmation wording is a product decision" and watch it return DECISION NEEDED.

Step 7. Try to fake "done" (the second hook)

Write evals for FR-02, approve them, then, before running the loop, say: "Mark FR-02 as done."

Blocked with a list: EV-01 is PENDING ... EV-02 is PENDING. "Done" is only possible when the gate passes.

Now run /solo-review:review-loop FR-02 and let it finish.

Step 8. The blind user (10 minutes)

/solo-review:first-time-user Write down something you need to do today, then tick it off when you finish it

The skill starts the app with throwaway data (so your real data is never touched), then sends the first-time-user agent with only the URL and your sentence. It sees no code, no docs and no shell. The report lists stuck points as Blocked, Confused or Slow. Typical finds: no sign that the field is required, no feedback after Add, a checkbox that is hard to hit on a phone. The skill saves the report as .review/ftu/<date>-<feature>.md, stops the app, and suggests a fix for each stuck point. It applies none of them.

If the agent tries to read a file, the hook answers: first-time-user may only use browser tools. Its tool list is also limited to browser tools, so there are two separate blocks.

Pick one stuck point to keep. Fix it with /solo-review:write-evals (a new check) or /solo-review:fix-a-bug.

Step 9. Report a bug (5 minutes)

/solo-review:fix-a-bug Adding a task made only of spaces should show an error, but it seems to add an empty task

Two outcomes teach something. If the builder handled it, the skill tries to reproduce, cannot, says so with what it tried, and stops without touching code. If the bug is real, it reproduces it, states a guess about the cause, tests the guess, finds the change with git, fixes it on a fix/... branch, keeps the failing test as a regression test, adds a new regression check to the feature's eval.md (result PENDING, so the verifier confirms it in the next loop), and tells you how to undo the fix (git revert <sha>).

Step 10. Teach the reviewer

When the loop finishes, it proposes one-line rules for REVIEW.md §7 from findings that came back in two rounds or more. Read them. Say yes only to rules that are true and general. An example of a good rule: "Every text input must be trimmed and length-checked on the server, not only in the page." The skill appends each approved line to section 7 of REVIEW.md. Next feature, every agent reads it, because CLAUDE.md loads REVIEW.md at the start of each session.

Check the evidence yourself. The gate proves that the verifier wrote PASS with evidence. It cannot prove the verifier was right. Spend 2 minutes opening the screenshots for any feature that matters. That small human step is what the article means by "reading the evidence".

9. Cost and control

  • One loop round starts 3 fresh agents (builder, verifier, reviewer), and the verifier drives a real browser. A feature that passes in round 1 costs one round. A stuck feature costs up to 5.
  • The article gives the reason for the stop rules. One pull request went through more than 50 rounds of review and fixes overnight. About 59% of what the reviewer flagged was code that had been there since round 1. So: (a) stop after a cap, (b) re-review only the new diff, (c) name the class of problem so one fix covers all instances, (d) never repeat a finding.
  • Anthropic's own cap is 3 rounds. This kit uses 5, because one round here builds, checks every eval in a browser and reviews the code. That is the AI Labs choice. Change max_rounds in templates/state.md and the numbers in skills/review-loop/SKILL.md if you want 3.
  • Risk is the main dial. Low needs 3 checks, medium 5, high 8. Rate honestly: not everything is high.
  • For scale: Anthropic's paid Code Review product (Team and Enterprise plans) averages $15 to $25 per pull request. It is not part of this kit and you do not need it.

10. What is left out, and why

The article describes seven layers. This kit covers the ones that make sense for one person.

Article layerIn this kit?
1. Verify before anyone looks (tests, screenshots, subagent review, evals)Yes. This is the core: evals, verifier, reviewer, REVIEW.md.
2. AI review on every pull requestReplaced. A solo workflow often has no pull requests, so the reviewer reads a diff file between commits. The paid product and the GitHub Action stay optional.
3. Security review that blocksPartly. REVIEW.md §3 has a secrets check. Run /security-review yourself for high-risk features.
4. Automated checks that block (lint, types, tests, build)Yes, through the builder's pre-handoff run and the verifier's production build.
5. Human approval scaled by risk (0, 1 or 2 people)Replaced. A solo builder is the only person. Risk instead sets how strict the evals are, and "reviewed" always needs your confirmation.
6. Merge queue, flags, gradual releaseNo. Add feature flags and staged releases if you ship to real users.
7. Fast detection and rollbackPartly. Git branches and commits give rollback. Add monitoring when you have users.

12. Honest limits

  • The hook is checked by a self-check, not yet by a real subagent run. The hook was tested with simulated tool calls (all assertions pass) and the plugin passes validation. No live subagent run is recorded. The first-time-user block depends on Claude Code passing agent_type to the hook; the agent's own tool list is the second block. Step 8 of the walkthrough is the live test. If a Read succeeds there, report it as an issue.
  • The "reviewed" confirmation is a hook permission prompt. It was not observed in a live session. It may not appear in bypass-permissions mode. Step 5 is the live test.
  • The gate only sees the file. It cannot tell that an eval is weak. Reviewing the evals before the build (Step 3) is the control for that.
  • The verifier is a model. It can write PASS wrongly. The evidence line and screenshots exist so you can check.
  • A shell command can still change files in ways the hook does not parse. The hook blocks the common status: edits through the shell, not every possible one.
  • Anthropic's numbers come from a team with a large codebase. They show the direction, not what you will measure alone.
